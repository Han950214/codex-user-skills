# 系统化调试

围绕一个能捕获用户实际症状的失败信号推进，不用猜测替代证据。

## 流程

1. **建立失败信号**：优先使用现有单元、集成或端到端测试，其次使用 CLI、固定 fixture、现有浏览器脚本或最小 harness。信号必须能对当前问题判红和判绿。
2. **复现**：运行该信号，记录命令、症状和稳定性。非确定性问题要提高复现率并记录频率。
3. **最小化**：逐项减少输入、步骤、数据或依赖；每次只改变一个变量，保留所有必要条件。
4. **提出可证伪假设**：列出三至五个排序后的假设，并为每个假设写明可观察预测。可以向用户展示最高优先级假设，但不要因等待答复阻塞继续取证。
5. **收集证据**：优先调试器、边界值检查和有唯一前缀的定向日志。性能问题先建立基线，再分析 profiler、计时或查询计划。
6. **修复根因**：只修改能解释证据的最小根因，不用绕过、吞错或扩大范围掩盖症状。
7. **回归验证**：有正确测试 seam 时先将最小复现固化为失败测试，再确认修复后通过；同时重跑原始场景和相关回归。
8. **清理**：删除本轮调试日志、临时 harness 和诊断开关，复核没有遗留调试代码。

## 安全与项目适配

- 遵守当前用户指令、项目 `AGENTS.md`、阶段范围和现有 Git 改动；不得修改其他仓库。
- 不自动用 `git bisect` 切换工作区，除非当前任务明确授权；不得执行 `git reset`、`git clean` 或 `git rebase`。
- 浏览器问题优先复用项目已有 Puppeteer、Playwright、Chrome for Testing 或现场验收脚本，不安装新浏览器、系统软件或依赖。
- 不要求用户频繁回答问题；只在缺少授权、环境或关键证据时请求最小必要输入。
- 无法建立自动复现时，明确列出已尝试方法、缺失证据和验证限制，不把未经验证的推测报告为根因。
