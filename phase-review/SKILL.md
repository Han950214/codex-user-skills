# 阶段复核

保持只读，把阶段规格和当前 Git 证据作为权威来源。找不到 Issue、PRD 或特定 tracker 时不要中止，也不要要求用户重复提供当前任务中已有的规格。

## 固定比较点

依次选择并验证一个固定点：

1. 当前阶段指令明确给出的 baseline commit；
2. 当前任务开始时记录的 `HEAD`；
3. 当前分支相对 `origin/main` 的 merge-base；
4. 最后才使用有证据支持的本地固定点。

记录固定点、当前 `HEAD`、提交列表、工作区和 index 状态。固定点无效或 diff 为空时如实报告，不自行换成更方便的比较范围。

## 检查清单

- 目标和阶段规格是否完成，是否存在遗漏或范围外行为；
- diff 是否只包含本阶段内容，是否误改其他仓库或用户现有改动；
- 是否引入无调用方 DTO、registry、wrapper、adapter 或投机抽象；
- 是否存在正确性、错误处理、并发、数据一致性或兼容性问题；
- 是否存在安全、隐私、secret 或权限扩大问题；
- 是否有与风险相称的回归验证，测试是否真实覆盖声明；
- 用户可见 UI 是否完成真实运行、截图和要求的视觉复核；
- 文档和界面文案是否夸大真实能力或隐藏数据来源限制；
- 是否执行了当前任务禁止的 Git、系统或远端操作。

按严重程度报告可操作发现，给出文件和紧凑行号证据；没有发现时明确说明剩余验证限制。不要用无证据的风格偏好制造问题。

## 行为边界

`phase-review` 本身不得修改代码、创建 commit、push、amend、创建分支或操作 Issue Tracker。内部质量门禁结束后，主任务可在原范围内修复发现并重新验证。

默认不启动多个子代理。只有完整阶段、diff 较大且独立视角确有价值时，最多使用两个只读子代理；分配不重叠的检查面，禁止重复扫描整个仓库。该复核不能替代用户随后要求的独立审核。
